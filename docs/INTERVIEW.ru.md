# Как объяснить Relay Ledger

Покажи реальный сценарий `python scripts/smoke.py`: один запрос, его повтор, затем попытки доставки 503 → 503 → 200. Открой историю и тест параллельного claim.

Вопросы для самостоятельного разбора:

1. Где заканчивается идемпотентность API и начинается идемпотентность получателя?
2. Что случится, если получатель обработает событие, а worker упадёт до записи успеха?
3. Зачем lease token, если уже есть lease timeout? Разбери завершение старого worker после нового claim.
4. Почему HTTP выполняется вне транзакции SQLite? Что будет при долгом сетевом ответе?
5. Почему 429 повторяется, а 400 и redirect — нет? Какие ограничения у текущего backoff?

Практика: убей worker во время доставки, дождись истечения lease и восстанови обработку. Следующее самостоятельное расширение — Retry-After с ограничением максимальной задержки и тестами некорректного заголовка. Отдельно спроектируй безопасный ручной replay dead-letter, не сбрасывая историю попыток.

Это AI-assisted личный проект с at-least-once семантикой. Не обещай exactly-once, горизонтальное масштабирование SQLite или production SLA. Для DevOps важны наблюдаемое состояние очереди, восстановление и понятные границы отказа.
